# Security self-review (OWASP ASVS 5.0)

A self-review of secure-call against the
[OWASP Application Security Verification Standard 5.0.0](https://github.com/OWASP/ASVS/tree/v5.0.0_release/5.0),
**Level 2**, for the parts that apply. It covers both repositories and the Raspberry Pi
deployment. It is a self-review, not an outside audit: see [For outside reviewers](#for-outside-reviewers).

**Reviewed at:**

- [secure-call](https://github.com/The-Secure-Video-Call/secure-call) `296aa9457267c1b1d87daee1f6928fc256cfd52b`;
- [secure-call-backend](https://github.com/The-Secure-Video-Call/secure-call-backend) `89b598e989df778581c62872fd58b4fd2d2c340e`.

**How to read it:**

- Every requirement of ASVS Level 1 and Level 2 is listed with its ID and marked **Met**,
  **Not met** or **Not applicable**. Level 3 requirements are left out.
- Partly met counts as **Not met**, with what is missing.
- Every **Met** cites its evidence as `repository:path:line` at the commits above, or a test.
- Requirements that depend on the hosting or on the Pi, where the repositories hold only
  documentation, say so.
- Every **Not met** is listed again under [Gaps](#gaps), with a severity and a suggested fix. This
  document fixes nothing; the gaps become issues.
- **Live checks** were read-only, on 2026-11-10 and 2026-11-11: `curl -sSI` against
  https://securevideocall.com/ and https://signal.securevideocall.com/healthz, a few TLS version
  and cipher probes, TRACE and plain-HTTP redirect probes of both hosts, and the GitHub API. There
  was no load, no fuzzing, and no TURN traffic.

## Threat model in short

The full threat model is [docs/threat-model.md](threat-model.md), and the design is
[PLAN.md](../PLAN.md) §3. In short:

- **What a call is.** Two people share a link. Its fragment (`#secret`) is never sent to a server.
  - **Keys:** the browser derives, with HKDF-SHA256, a `roomId` that it sends to the signaling server
    and a `signalKey` that never leaves the browser.
  - **Signaling:** every offer, answer and ICE candidate is AES-256-GCM encrypted. The sender's role
    and a message counter go in the additional data, so the server can't read, change, replay,
    reflect or reorder them.
  - **Media:** WebRTC DTLS-SRTP, directly or through our TURN relay.
  - **Safety code:** a short code from both DTLS fingerprints. It is meant to show a man in the middle
    if the two people compare it. At the reviewed commit, a man in the middle who has the link could make both codes match
    ([V11.4.3](#high), High); fixed after this review by a commitment to each fingerprint in the
    `hello` (issue #94).
- **What the servers can still see** (PLAN.md §3.3):
  - **The signaling server:** the room ID, both IP addresses, when a call starts and ends, and the
    size and timing of the encrypted messages.
  - **The TURN relay, when it is used:** both IP addresses, how long the call lasts, and how much data
    it carries.
  - **Nobody:** video, audio or the room secret. The safety code is not a secret: with DTLS 1.2 the
    certificates travel in the clear, so anyone on the media path can work it out.
  - **Nothing is stored:** rooms and rate-limit counters live in memory only.
  - **Nothing is logged by the applications:** no IP addresses, room IDs or message contents. The
    reverse proxy in front of the backend is a gap (V14.2.4).
- **The web app trust problem** (PLAN.md §3.4). The app is only as trustworthy as the JavaScript the
  static host sends. Whoever controls that host could ship code that leaks the secret, the keys or
  the camera, and the safety code can't detect it, because changed code could show a matching code.
  - **The mitigations:**
    - a strict CSP with Trusted Types, and no third-party code;
    - Subresource Integrity, which catches a changed asset next to an unchanged `index.html`, but not a
      host that changes `index.html` too, since the hashes are in it;
    - a reproducible build, built twice on two operating systems on every deploy;
    - attested `web-<commit>` releases;
    - `scripts/verify-deployed.mjs`, so anyone can check that the live site serves exactly a
      release of this repository;
    - static hosting kept separate from signaling.
  - **What they can't do:** stop a compromised host from serving other code to some visitors. A check
    only covers the copy the checker receives, so code served only to chosen visitors goes unnoticed
    by everyone else's checks.
- **Who we defend against:** a network attacker, a malicious or hacked signaling server, a
  compromised static host (detection only), a leaked link, and the other person learning your IP
  address (privacy mode).
- **Not covered:**
  - denial of service;
  - a compromised device or browser;
  - people who don't compare the safety code;
  - proving who the other person is (there are no accounts).

**The most important findings:**

- **One High: [V11.4.3](#high)**, fixed after this review (issue #94). The 36-bit safety code had no
  commitment step. A man in the middle who has the link and controls signaling could choose certificates so that both safety codes matched. That defeated the safety code in the case it was designed for. The fix commits to each DTLS fingerprint in the encrypted `hello` before any SDP is sent.
- **Two Medium: [V14.2.3 and V14.2.4](#medium).** With privacy mode off (the default), Google and
  Cloudflare STUN see both IP addresses. The reverse proxy in front of the backend logs client IP
  addresses, outside the apps' "no IP logging" rule.
- **The rest is Low:** hardening, missing policies and inventories, out-of-date docs, and two logging
  requirements this project doesn't meet on purpose, for privacy.
- **What holds up well:**
  - the end-to-end design: encrypted and authenticated signaling, with replay and reflection
    protection; strict schemas on both sides; and the Origin check;
  - the room, rate and connection limits, though capacity can still be used up within them
    ([V17.3.1](#low));
  - the CSP with Trusted Types, SRI and no third-party code;
  - privacy mode that never falls back to a direct connection;
  - pinned and audited dependencies, and a reproducible, attested build that anyone can check
    against the live site.

**Whole chapters that don't apply:** V5 File Handling, V10 OAuth and OIDC, and almost all of
V6 Authentication. The app has no accounts, passwords, logins, sessions, cookies, file uploads or
third-party sign-in. V7, V8 and V9 apply only in part: to the WebSocket connection, to access to a
room, and to the TURN credentials.

## V1 Encoding and Sanitization

The app has no free-text features (no chat, no names, no uploads). The only untrusted inputs are the URL fragment, server messages and the peer's encrypted payloads, and React renders all of them as text under a CSP that enforces Trusted Types and allows no policy. Neither server builds HTML, queries a database, runs commands or calls other services with user data.

## V3 Web Frontend Security

The web app is a static React bundle on Apache. It gets a strict set of headers from `.htaccess`, which is checked at build time and again before deploy. The signaling server serves only `/healthz` and the WebSocket, on its own hostname. There are no cookies, no CORS, no `postMessage` and no third-party scripts (`secure-call:apps/web/build-tools/indexHtmlCheck.ts:59-61,79-82` rejects inline and off-origin scripts). SRI on every script and stylesheet, an L3 item (V3.6.1), is also in place.

## V8 Authorization

Access to a call is a capability. Whoever holds the link, the 32-byte secret in the fragment,
derives both the room ID and the `signalKey` (`secure-call:apps/web/src/crypto/roomId.ts:10-18`,
`apps/web/src/crypto/signalKey.ts:12-22`). The server sees only the room ID, and it enforces seats,
expiry and membership.

Can someone who knows only the room ID (not the secret) join? Yes: the server cannot tell them from
a real caller, and the Origin check is no barrier for a non-browser client. They can take a free
seat. They cannot read or inject anything:

- every relayed payload must decrypt under the `signalKey`;
- any failure ends the call with a warning;
- local tracks are added only after a valid encrypted `hello`, so no media reaches them.

So the most they can do is deny service. In practice only the server side holds room IDs: they are
never logged, and group names are hashed (`secure-call-backend:signaling/rooms.py:33-35`). The
threat model already concedes that a hostile server can refuse service
(`docs/threat-model.md:36`).

## V11 Cryptography

## Gaps

Every **Not met** above, by severity, with a suggested fix. Nothing here is fixed in this document;
each becomes an issue.

**Severity:**

- **High:** exploitable now against the confidentiality or integrity of calls, under the preconditions
  given.
- **Medium:** a real weakness with limits.
- **Low:** hardening or documentation.

**"On purpose"** marks a requirement this project does not meet by design, for privacy. The fix
there is optional.

### High

- **V11.4.3: the safety code can be matched by a man in the middle.** _Fixed after this review by
  the fingerprint commitment in the `hello` (issue #94; `docs/protocol.md` section 5)._ The code is the first 36
  bits of SHA-256 over the two DTLS fingerprints, and nothing binds it to anything sent earlier.
  - **Where:** `secure-call:apps/web/src/crypto/safetyCode.ts:9,158-168`.
  - **Who:** someone who has the link and controls the signaling path, such as a malicious server
    with a leaked link: the exact case PLAN.md §3.1 relies on the safety code for.
  - **How:**
    1. He runs two separate legs, and sends each side his own `hello`. The hello carries only a session
       ID (`secure-call:apps/web/src/rtc/callSession.ts:373-376`).
    2. He never offers, so both honest sides offer and reveal their fingerprints
       (`callSession.ts:266-270`, `perfectNegotiation.ts:62-71`).
    3. He holds back his own SDP until he has seen both fingerprints, then answers each side
       (`perfectNegotiation.ts:113-121`) with a certificate from a pool made in advance, chosen so
       the two codes collide.
  - **Cost:** about 2^18 fingerprints per side give one collision on average, and 2^19 give about 98%.
    Once he sees the real fingerprints, the search takes milliseconds, and nothing times out.
  - **Impact:** both people see the same six symbols and press "Yes". Threat-model limit 5 (a man in
    the middle heard for "the first seconds") becomes the whole call. `docs/threat-model.md` does not
    list this.
  - **Fix:**
    - **Symmetric commitments, checked against the SDP:** each side's `hello` carries a full-length
      commitment to its own DTLS fingerprint, `SHA-256("secure-call/fp-commit/v1" ‖ normalised
fingerprint)`.
      - Before computing or showing the code, each side checks every fingerprint in the peer's SDP
        against the peer's commitment, and any mismatch fails verification.
      - No SDP leaves before the peer's hello is accepted (already true), so he has to fix his
        certificate on each leg before either honest side reveals anything. No extra round trip is
        needed. No nonce is needed either: the fingerprint of a fresh key can't be guessed.
    - **A fresh certificate for every `RTCPeerConnection`:** made with
      `RTCPeerConnection.generateCertificate()` as ECDSA P-256 and passed in `certificates`, never
      reused or stored. Otherwise he could force a reconnect, learn both fingerprints in a throwaway
      attempt, and search before the real one.
    - **The schema requires the commitment:** no fallback to a hello without one.
    - **What is not enough:**
      - a commitment from one side only, while the other side reveals its fingerprint without waiting;
      - a commitment that is never checked against the SDP;
      - certificates reused across connections.
    - **Afterwards:** his chance drops to 2^-36 per attempt. Record the 36-bit code as a documented
      short-authentication-string exception, since it still doesn't meet V11.4.3's letter (at least
      128 bits). Add a negative test for each mismatch, and update PLAN.md §3.2 and the threat model.

### Medium

- **V14.2.3: third-party STUN sees everyone's IP address by default.** Privacy mode is off by
  default. With it off, every call sends both people's IP addresses and call times to Google's and
  Cloudflare's STUN servers.
  - **Where:** `secure-call:apps/web/src/rtc/iceServers.ts:3-10`, still marked `TODO(M3)`. The threat
    model documents it.
  - **Fix:** use our own coturn for STUN (`stun:turn.securevideocall.com:3478`), remove
    `PUBLIC_STUN_ICE_SERVERS`, and update `docs/threat-model.md`.
  - **Status:** fixed in #95. The only STUN server is now our own coturn (`OWN_STUN_ICE_SERVERS`).
- **V14.2.4: the "no IP logging" rule stops at the apps.** Nginx Proxy Manager logs every client's
  IP address and connection time by default, and the static host and its CDN keep their own access
  logs.
  - **Fix:**
    - `access_log off;` alone is not enough: nginx error-log lines contain `client: <IP>`, for
      example the routine "recv() failed … while proxying upgraded connection". An `error_log` in
      the Advanced tab adds a second destination rather than replacing the template's;
    - also discard the proxy host's error log, or put NPM's `/data/logs` on a tmpfs, and document
      the retention in the Pi setup steps;
    - first delete the access and error logs already written under `/data/logs`, logrotate copies
      included: a tmpfs mount only hides files already on the disk;
    - NPM's fallback (default-host) access and error logs record client IPs too, and the per-host
      `access_log off;` does not touch them; the tmpfs covers them from then on;
    - record the static host's and the CDN's logging and retention in PLAN.md §3.3.

### Low

**Session and protocol**

- **V7.3.1, V7.3.2:** after `leave`, the server never closes the socket. It can stay open,
  answering pings, up to Daphne's undocumented 24 h `websocket_timeout`, holding a connection slot.
  It can also `join` again, so the 4 h room limit doesn't bound the session either. Only a
  hand-written client does this.
  - **Fix:** start the join timeout again after `leave`, and set `--websocket_timeout` just above
    the 4 h room limit in the `Dockerfile`, with tests for leave-then-idle and leave-then-rejoin.
- **V7.1.1:** the docs give the join and room limits, but not the socket's limits after `leave` or
  its absolute cap. `PLAN.md:66` says "10 min with nobody in it" where the code means one person
  alone.
  - **Fix:** document the socket limits in the backend README, and correct `PLAN.md:66`.
- **V9.2.1:** coturn 4.18 accepts a Refresh with an expired TURN credential, so a relay allocation
  can outlive its credential and its room. Credentials are not revoked on `leave` either. This
  affects relay availability only: media stays encrypted and the deny list still applies.
  - **Fix:** accept it as a residual risk. Keep the CI check (`test-coturn.sh:456-467`) that notices
    a change in a coturn upgrade, and revisit if coturn gets a cap on allocation lifetime.
- **V15.2.2:** the web client has no timeout between `hello` and the first offer, and no cap on its
  incoming message queue (also threat-model limit 7).
  - **Fix:** end the call if no offer **or answer** arrives within N seconds of the peer's `hello`,
    and fail verification above N queued messages. The impolite side may receive only an answer, so
    "no offer" alone would end real calls.
- **V17.3.1, V2.4.1:** capacity can be used up within the limits.
  - **Connections:** the global cap of 500 can be filled from 25 IPv4 addresses (two IPv6 /48s), and

  - **Fix:**
    - fix V7.3.1 first;
    - then consider an idle timeout for joined sockets whose room has had no partner for some
      minutes;

  - **Fix:** `AddDefaultCharset UTF-8` and `AddCharset utf-8 .js .css` in `.htaccess`, checked by

## For outside reviewers

Thank you for looking. This section is for anyone who reviews secure-call from outside the project.

### Scope

- **[secure-call](https://github.com/The-Secure-Video-Call/secure-call):** the web app, served as
  static files from shared Apache hosting behind a CDN (StackCDN) at https://securevideocall.com, and its build and deploy
  workflows.
- **[secure-call-backend](https://github.com/The-Secure-Video-Call/secure-call-backend):** the
  signaling server (Django Channels on Daphne, `wss://signal.securevideocall.com`), the TURN relay
  (coturn), and the Raspberry Pi deployment that runs both (`deploy/raspberry-pi/`).
- **Out of scope:**
  - the hosting company's own infrastructure;
  - GitHub;
  - the public STUN servers used with privacy mode off;
  - denial of service by volume.

The most interesting questions are in [docs/threat-model.md](threat-model.md). Can a malicious
signaling server, a network attacker, someone with a leaked link, or the other person learn more
than the threat model says? Can a compromised static host go unnoticed by
`scripts/verify-deployed.mjs`?

### Running everything locally

**Web app** (Node from `.node-version`, pnpm 10+):

```sh
pnpm install --frozen-lockfile
pnpm --filter @secure-call/web dev          # http://localhost:5173
pnpm lint && pnpm typecheck && pnpm test && pnpm build
pnpm --filter @secure-call/web check:build  # SRI, no inline code, headers intact
node --test 'scripts/*.test.mjs'
```

**Signaling server** ([uv](https://docs.astral.sh/uv/) installs Python 3.14):

```sh
uv sync --locked
DJANGO_DEBUG=1 uv run daphne -b 127.0.0.1 -p 8000 config.asgi:application
uv run pytest && uv run ruff check && uv run mypy . && uv run pip-audit --strict
```

**A full encrypted call in two real browsers,** under the production CSP (the web repo's
`apps/web/e2e/`, which needs a checkout of the backend):

```sh
VITE_SIGNALING_URL=ws://localhost:8000/ws/signal/ pnpm build
cd apps/web
pnpm exec playwright install chromium firefox
E2E_BACKEND_DIR=/path/to/secure-call-backend pnpm test:e2e
```

**The TURN relay's configuration** (needs a Linux Docker host with `python3` and `ip`: its probes reach the container's address from the host, which Docker Desktop on macOS or Windows doesn't route): `deploy/raspberry-pi/coturn/test-coturn.sh` in the
backend. It starts the pinned coturn image with a test secret, and checks:

- that valid, wrong and expired credentials are handled correctly;
- that private and denied peers are refused.

**The live site against its published release:** `node scripts/verify-deployed.mjs` (see
[SECURITY.md](../SECURITY.md#verify-the-app-youre-running)).

Please don't load-test or fuzz the live servers. Run things locally instead. They are small and
shared: the signaling server and the TURN relay run on one Raspberry Pi.

### Reporting findings

Report through GitHub private vulnerability reporting, as described in
[SECURITY.md](../SECURITY.md): the repository's **Security** tab, then **Report a vulnerability**.
Never include a real call link: the part after `#` is the call's secret.
